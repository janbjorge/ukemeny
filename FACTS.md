## 2. Layout

- `src/core/`: the pure domain. models.py (types; `Dish` and `Part` are what the site keeps, `Traits` is a row of the vocabulary, `Snapshot` holds them), diet.py (`judge`: does a dish fit a `Household`), matching.py (our `CATEGORIES`, the offer word filter, weights, `main_protein`), ranking.py (`dinners`, `varied`, the `FLOOR_KR` a dinner must save), dishes.py (full recipe → `Dish`, the `form` a line asks for), search.py (`parse` bokmål into clauses, `tags` per dinner, `Index` to find), ports.py, errors.py. Standard library only; tests/test_boundary.py enforces it.
- `src/app/queries.py`: read-only queries over the snapshot for the site, the API and the CLI (`search`, `tally`, `check`). The search index is worked out once at start-up, a ranking when a search first needs it (the index in 0.03 s; a search with a new word took at most 9 ms, 2026-10-13).
- `src/app/build.py`: the offline use cases: `recipes` (the pages), `draft` (a row in the vocabulary for each new ingredient name: its category, then its facts), `filed` (every ingredient's category from the vocabulary), `match` (offers), `snapshot` (all of it), `reprice` (the offers only, for `--offers`).
- `src/adapters/`: datasets.py (reads and writes `datasets/`, implements `core.ports.Datasets`), profile.py (profile.yaml with pydantic), schema.py (the JSON shape for API and CLI), cli.py, and `web/` (main.py, api.py, params.py for query strings, fmt.py for Norwegian numbers, templates, static).
- `src/pipeline/`: offline only, not in the Docker image. matprat.py and godt.py (the recipe sources, reading pages through pages.py), tjek.py, jev.py, datasets.py (the composition root: `uv run python -m pipeline.datasets`).
- `profile.yaml`: our household and its place, for the CLI (§5); the site and the build do not read it. `src/adapters/profile.example.yaml` is the template, identical today (tests/test_profile.py).

Site quirks:
- matprat's `__NEXT_DATA__` holds each ingredient's name, amount, unit and grocery department (`/kjøtt/kylling/høns`, `/melk/melkeprodukter`, `/glutenfritt`, `/melkefritt`), and `gtmDimensions.dimension8` = `Middagsrett` marks dinners (1 943 of 4 479). matprat's own main ingredient (`dimension1`) misfiles some dishes ("Kyllingfilet med spekeskinke" is Svin), so it is not used (METHOD.md §3).
- matprat's robots.txt disallows `/Services/` (its search API) and allows `/oppskrifter/`, so pages are read one by one. robots.txt asks for no crawl delay; 16 at a time read 300 pages in 29.5 s with no errors (2026-10-13), so a full crawl is about 7 minutes. It used to be 3 at a time with half a second between (about 40 minutes).
- godt.no's `__NEXT_DATA__` (`props.pageProps.recipe`) holds each ingredient's name, amount, `maxAmount` («1 - 2 ss») and unit, but no grocery department (the build gives one, METHOD.md §2); the minutes before, during and after cooking; the portions; the rating and votes; and tags, where «Middag» marks dinners (1 455 of 3 896, 2026-10-14). The title is `recipe-top`'s, the page's h1; JSON-LD's `name` is one for search engines («Tomatsuppe - Hjemmelaget, rask og skikkelig god» for «Hjemmelaget tomatsuppe»).
- godt.no's robots.txt asks for no crawl delay and shuts out only a list of AI crawlers by name (GPTBot, ClaudeBot, CCBot, anthropic-ai, …); matris's user agent is not one of them. The site is behind AWS WAF: 8 pages at a time (about 38 a second) got 2 681 pages in about 70 s, then `202` with no body and `x-amzn-waf-action: challenge` for the other 1 215, still about 5 minutes later (2026-10-14). The build reads it at 4 pages a second (`PER_SECOND`). The 2026-10-14 crawl of every page (3 896) took 16 minutes; the index is now the dinner list (METHOD.md §7). A challenge counts as a failed page; before that, the build read the challenges as pages without a recipe and lost 820 of them unnoticed.
- Tjek: one location search stops at 1 000 offers, so offers are read per catalog. Catalogs are regional: of the 20 places (15 km around each, 2026-10-13) only REMA 1000 and Europris had one catalog in all; Extra had 6 regional catalogs, Bunnpris 4, KIWI and SPAR one for the south and one for the north, and Obs one per store. Together 39 catalogs and 2 631 offers (925 different headings) in about 1 s; per place 580 (Tønsberg) to 1 015 (Oslo) offers; Stavanger 997, as when it was the only place. The catalogs in every place listed 260 offers. A catalog's listed `offer_count` can differ from what `/offers` serves (KIWI listed 109, served 105).
- Tjek also lists furniture, hardware and electronics catalogs; "Spar Kjøp" is building supplies. Only the chains in `GROCERS` (src/pipeline/tjek.py) are read.
- Before-prices: Tjek's `pre_price` field, or "Førpris 34,90" / "Før 48,9" in the catalog text (mostly Joker). On 2026-10-13, discounted/all offers per chain: Bunnpris 0/161, Matkroken 0/10, Europris 36/152, Coop Mega 47/119, KIWI 27/105, Extra 28/103, REMA 1000 27/89, Joker 39/68, Obs 9/50, Coop Prix 10/45, MENY 11/35, Coop Marked 4/32, SPAR 14/28.
- Coop Mega prices some weighed goods per 100 g against a before-price per kg ("29,90 … Pr kg 299,00. Førpris 339,00 pr kg"), which read as 91 % off instead of 12 % (METHOD.md §4).

## 4. Data and the weekly build

- `datasets/` is committed and is all the site reads: dishes.json (3 401 dinners: 1 945 from matprat.no and 1 456 from godt.no, 7.4 MB), traits.json, the vocabulary (1 745 ingredient names, 1.1 MB): per name its facts, `category` (one of ours, core.matching.CATEGORIES; the same strings as a part's), `product` (what the name is in the shop; the name itself until set), `source` (`hand`, or the Jev model that drafted the row) and, for a name a recipe counts in pieces, `piece_g` (grams per stk; docs/plan-per-person.md). It is kept between builds and fixed by hand, never rebuilt (jb 2026-10-22; docs/plan-model.md), and tests/test_traits.py reviews it: every name in dishes.json has a row, every part's category is its row's, and no row contradicts itself or its category (a /kjøtt row holds meat, a /grønnsaker row no egg; hvalkjøtt and ferdig potetmos are the named exceptions). Seeded on 2026-10-22 from the build of 2026-10-14 with 61 rows fixed by hand, and 37 more on 2026-10-23 (METHOD.md §2). offers.json (`built`, the offers, each with its `catalog` and, since 2026-10-24, what its price buys (`size`, `size_to`, `unit`, `pieces`; docs/plan-per-person.md), `matches`: per ingredient name the discounted offer ids that are that ingredient, `served`: the same per dinner URL for meat, fish and shellfish, and `places`: per place the catalogs near it; 1.4 MB). The build of 2026-10-13 20:11 UTC, the first with places: 2 631 offers from 39 catalogs (580 in Tønsberg to 1 015 in Oslo, 997 in Stavanger), and 159 ingredient names matched to 1 022 offer ids (before places: 157 names, 399 ids). The build of 2026-10-14 14:10 UTC, the first with godt.no: 2 632 offers, and 231 names matched to 1 672 offer ids. The build of 2026-10-23 05:40 UTC (jb's run, commit 62134ab), the first on the vocabulary and with a form per part: 3 596 offers, 56 names matched by product, meat or fish on offer for 1 150 dinners, and one row drafted (perlepoteter). src/adapters/datasets.py also reads an offers.json from before places (no `catalog` or `places`) as every store with no place known.
- A dish in dishes.json is facts, no rules (jb 2026-10-13: "there are loads of other constaints that might apply, so we can not have these attched to the dish"): name, URL, portions, prep time, rating, and per ingredient its name, its category (from the vocabulary), unit, grams per portion rounded to 5 g, pieces per portion for a line counted in pieces (since 2026-10-24; docs/plan-per-person.md), and the form the line asks for (core.dishes.FORMS: røkt, hermetisk, frossen, …; "" for what the name alone means), which only the offer matcher reads. No ingredient wording and no method: the repo is public and the recipes stay on matprat.no and godt.no (docs/plan-web.md). Every rule (lactose, onion, main protein, discount weight) is worked out from these and the traits at runtime.
- `uv run python -m pipeline.datasets` (or `matris build`) builds dishes.json and offers.json from scratch, with nothing kept between runs except the vocabulary, traits.json, which it reads and adds to, and, with `--known`, the list of godt.no pages. godt.no's dinners come from `https://www.godt.no/oppskrifter/middag` (24 a page; 1 456 on 2026-10-22), since `/sitemap-recipes.xml` is 404. `--known` reads the godt.no URLs already in dishes.json instead (jb: "we need some kind of refresh option that uses the dishes we know allready"); those pages are still read and parsed anew, and dinners added since are missed (jb 2026-10-13: "one thing, and one thing only, refresh from the sources, and build up or dataset, from scratch every time"; "ive told you to clean up the fucing cli"): every recipe page on matprat.no (4 479 pages, 16 at a time, about 7 minutes on 2026-10-13) and on godt.no (the dinner list, then each dinner at 4 a second; the 2026-10-14 build read all 3 896 recipe pages in about 16 minutes) at the same time (16 minutes for both on 2026-10-14, with matprat.no timing out and retrying now and then), this week's catalogs, a row drafted by Jev for each ingredient name the vocabulary lacks (its category, when neither a matprat line nor a name with the same words files it, then its facts; METHOD.md §2), a piece weight for each name a recipe counts in stk that lacks one (Jev's band read as grams, or the name's own «(ca. 1500 g)»; since 2026-10-24, METHOD.md §2), and every offer match; about 18 minutes in all on 2026-10-14, when every label of every name was still asked again. It needs `TYPESAFE_API_KEY` and shows a tqdm bar per step (matprat.no and godt.no, Jev's categories for new names, Jev's facts for new names, mattilbud.no, Jev's matches) with its count, speed and time left, and under it the URL matprat.no or mattilbud.no is being asked for (jb 2026-10-13: "THe cli needs some light output so i know whats going on"; "add tqdm and use that to track progress of the diffrent phases, also use to to how the current url getting fetched"). When jb asks for new data, the agent runs it.

With godt.no a ranking is 1.3 MiB (0.7 before) and a place's offers 1.1 MiB; warming every rule and place at start-up added about 60 MiB, so each machine thrashed (I/O stalls of 12–14 s, start-up up to 16 s, the front page 3–6 s) and was killed before warming was done. Now nothing is warmed, 8 rankings are kept (`Queries.KEPT`), the places' offers are dropped with them, and datasets/ is read one file at a time with one copy of each ingredient name (src/adapters/datasets.py). The site process on a Mac, which reads 20–25 MiB above Fly: 149 MiB after start-up, 165 after 100 searches over many rules and places; it was 216 and 251 with godt.no before the fix, and 165 and 185 before godt.no. - The app adds gzip, security headers and cache headers itself (src/adapters/web/main.py `headers`): hashed static files are immutable, pages, the front page too, 5 minutes. No stale-while-revalidate: with it a browser showed the page from before a deploy (2026-10-13). HEAD is answered like GET.
