## 1. What this is

Every HTML page links both in `<head>` and a `Link:` header. `/robots.txt` lets ChatGPT-User, Claude-User and Perplexity-User (agents fetching for a person) open everything, and for other crawlers allows `/api/` and keeps them off `/?` and `/middager` (not `/*?`: Python's parser let that outrank `Allow: /api/`, closing the API's searches; jb 2026-10-13); `/sitemap.xml` lists `/` and `/om`.

- Stack (as statsbudsjett): Python 3.14, FastAPI + uvicorn + Jinja + HTMX, no other JavaScript. pydantic v2 in the adapters, orjson for JSON.

## 2. Layout

- `src/core/`: the pure domain. models.py (types; `Dish` and `Part` are what the site keeps, `Snapshot` holds them), dishes.py (full recipe → `Dish`), diet.py (`judge`: does a dish fit a `Household`), matching.py (offer word filter, weights, `main_protein`), ranking.py (`dinners`, `plan`, `pick`, `varied`), search.py (`parse` bokmål into clauses, `tags` per dinner, `Index` to find), ports.py, errors.py. Standard library only; tests/test_boundary.py enforces it.
- `src/app/queries.py`: read-only queries over the snapshot for the site, the API and the CLI (`plan`, `search`, `check`). The search index is worked out once at start-up, a ranking when a search first needs it (the index in 0.03 s; a search with a new word took at most 9 ms, 2026-10-13).
- `src/app/build.py`: the offline use cases: `refresh` (recipes), `classify` (ingredients), `match` (offers), `snapshot`.
- `src/adapters/`: datasets.py (reads and writes `datasets/`, implements `core.ports.Datasets`), profile.py (profile.yaml with pydantic), schema.py (the JSON shape for API and CLI), cli.py, and `web/` (main.py, api.py, params.py for query strings, fmt.py for Norwegian numbers, templates, static).
- `src/pipeline/`: offline only, not in the Docker image. matprat.py and godt.py (the recipe sources, reading pages through pages.py), tjek.py, jev.py, datasets.py (the composition root: `uv run python -m pipeline.datasets`).
- `profile.yaml`: our household and its place, for the CLI (§5); the site and the build do not read it. `src/adapters/profile.example.yaml` is the template, identical today (tests/test_profile.py).

Site quirks:
- matprat's `__NEXT_DATA__` holds each ingredient's name, amount, unit and grocery department (`/kjøtt/kylling/høns`, `/melk/melkeprodukter`, `/glutenfritt`, `/melkefritt`), and `gtmDimensions.dimension8` = `Middagsrett` marks dinners (1 943 of 4 479). matprat's own main ingredient (`dimension1`) misfiles some dishes ("Kyllingfilet med spekeskinke" is Svin), so it is not used (METHOD.md §3).
- matprat's robots.txt disallows `/Services/` (its search API) and allows `/oppskrifter/`, so pages are read one by one. robots.txt asks for no crawl delay; 16 at a time read 300 pages in 29.5 s with no errors (2026-10-13), so a full crawl is about 7 minutes. It used to be 3 at a time with half a second between (about 40 minutes).
- godt.no's `__NEXT_DATA__` (`props.pageProps.recipe`) holds each ingredient's name, amount, `maxAmount` («1 - 2 ss») and unit, but no grocery department (the build gives one, METHOD.md §2); the minutes before, during and after cooking; the portions; the rating and votes; and tags, where «Middag» marks dinners (1 455 of 3 896, 2026-10-14). The title is `recipe-top`'s, the page's h1; JSON-LD's `name` is one for search engines («Tomatsuppe - Hjemmelaget, rask og skikkelig god» for «Hjemmelaget tomatsuppe»).
- godt.no's robots.txt asks for no crawl delay and shuts out only a list of AI crawlers by name (GPTBot, ClaudeBot, CCBot, anthropic-ai, …); matris's user agent is not one of them. The site is behind AWS WAF: 8 pages at a time (about 38 a second) got 2 681 pages in about 70 s, then `202` with no body and `x-amzn-waf-action: challenge` for the other 1 215, still about 5 minutes later (2026-10-14). The build reads it at 4 pages a second (`PER_SECOND`), 16 minutes for every page, and a challenge counts as a failed page; before that, the build read the challenges as pages without a recipe and lost 820 of them unnoticed.
- Tjek: one location search stops at 1 000 offers, so offers are read per catalog. Catalogs are regional: of the 20 places (15 km around each, 2026-10-13) only REMA 1000 and Europris had one catalog in all; Extra had 6 regional catalogs, Bunnpris 4, KIWI and SPAR one for the south and one for the north, and Obs one per store. Together 39 catalogs and 2 631 offers (925 different headings) in about 1 s; per place 580 (Tønsberg) to 1 015 (Oslo) offers; Stavanger 997, as when it was the only place. The catalogs in every place listed 260 offers. A catalog's listed `offer_count` can differ from what `/offers` serves (KIWI listed 109, served 105).
- Tjek also lists furniture, hardware and electronics catalogs; "Spar Kjøp" is building supplies. Only the chains in `GROCERS` (src/pipeline/tjek.py) are read.
- Before-prices: Tjek's `pre_price` field, or "Førpris 34,90" / "Før 48,9" in the catalog text (mostly Joker). On 2026-10-13, discounted/all offers per chain: Bunnpris 0/161, Matkroken 0/10, Europris 36/152, Coop Mega 47/119, KIWI 27/105, Extra 28/103, REMA 1000 27/89, Joker 39/68, Obs 9/50, Coop Prix 10/45, MENY 11/35, Coop Marked 4/32, SPAR 14/28.
- Coop Mega prices some weighed goods per 100 g against a before-price per kg ("29,90 … Pr kg 299,00. Førpris 339,00 pr kg"), which read as 91 % off instead of 12 % (METHOD.md §4).

## 5. The household and profile.yaml

- `diet`: onion, gluten, garlic each `avoid`, `note` or `ok`; `onion_substitute` (vårløk: fine for us and stands in for onion); `lactose` (grams per adult portion still fine, 3); `swaps` (false: only dinners needing no swap). `small_kids` (notes for chili and choking risks; no ages, since the repo is public). `place` (one of offers.json's `places`, any case; left out: every store). `week` (`dinners` 5, `fish` 2, `on_sale_only`).
- The site does not read profile.yaml. The CLI's base household is the profile's `diet` and `small_kids`; the words «uten løk», «glutenfri» and «lite laktose» in a CLI search add to it. `place` is where the CLI's offers are from unless `candidates --sted` names another; an unknown place is a setup error that lists the known ones. The build reads every place (§3). The Docker image does not contain the file.

## 6. Jev

- TypeSafe's Jev (typesafe_sdk, `jev-latest`, jev-1.13.0 on 2026-10-13), as in ezwork. Only the offline build calls it, at most 8 requests at a time.
- Ingredients: one Choice per label, from a registry (src/pipeline/jev.py `ingredient_labels`, keys in core.models.LABELS; jb 2026-10-13: "i want some kind of Choice regresety"): gluten yes/maybe/no, onion/garlic/maybe/none, lactose none/trace/some/high, kids ok/spicy/choking, then yes/maybe/no for each core.models.Item (the 13 EU allergens besides gluten, legumes, meat, animal origin, pork, alcohol), FODMAP low/moderate/high, carbohydrate per 100 g none/low/medium/high, and Mattilsynet's advice for pregnant women ok/limit/avoid. The state is the ingredient name and its matprat department. Every label of every ingredient is asked on every build, all in one request per ingredient.
- Departments: for each ingredient name only godt.no uses (596 on 2026-10-14; 448 more had a name matprat uses and took its department), one Choice over matprat's 35 departments with a dinner the name is in, after its labels, which go with that dinner instead of a department (src/pipeline/jev.py `JevDepartmentClassifier`, METHOD.md §2). 16 picks of meat, fish or dairy the labels did not agree with became /diverse and «maybe» in traits.json (and, grillspyd, vegetarfarse, isbiter, …).
- Offers: one yes/no question per offer heading, with the offer's text in the question, all in one request per ingredient. Every (ingredient, heading) pair is asked on every build, except that an exact name match or a snack/pålegg heading is answered without asking (src/core/matching.py `obvious`).
- What the probes showed (METHOD.md §2 has the judgement calls): Norwegian examples in the criteria fixed purre, risnudler, tamari and matfløte; the department fixed 28 of 36 wrong answers on rarer words; a single Choice over offers dropped right answers, and questions pointing at `offers[i]` mixed offers up. The new labels, probed on 64 hard ingredients (2026-10-13, /tmp/probe): 126 of 127 expected answers right at first, with vineddik and eggnudler as milk and dijonsennep as egg among the rest; naming them in the criteria made it 127 of 127 and cleared those three. That probe was 64 calls, 221 k tokens, $0.009.
- Cost: the first full classification and matching of 1 943 dinners was 1 503 calls, about 1.8 M input tokens, $0.074. Each build now asks everything again: with godt.no (2026-10-14) 2 896 calls, 10.7 M tokens, $0.451: the labels 1 744 calls and 7.8 M tokens, the departments 596 calls and 2.2 M, the offers 556 calls and 0.6 M. One build stopped on a single `499 Unable to complete this request` from Jev near the end of the labels; run again, it went through.
- Known wrong answers still in traits.json: hurtigris, malt allehånde and frossen lapskausblanding as gluten; gulbete and strutsevingknopper as onion. From godt.no (2026-10-14): ribberester without meat (with pork) and filed as /bær, margbein without meat, rundstykke as meat (/kjøtt/storfekjøtt, from «Baguette med pulled pork»), småløk with milk, and vegansk «kjøttdeig» as maybe meat; a scan of the names only godt.no uses for meat and fish words without meat, fish or shellfish found only the first two.

## 7. Hosting

- Dockerfile: python:3.14-slim plus uv, runtime dependencies only, no `src/pipeline/`, runs as `nobody`. The image is 406 MB and the app used 67 MiB of memory locally (2026-10-13). fly.toml: app `matris`, region arn, health check /helse, machines stop when idle, shared-cpu-1x with 256 MB, and it stays that size (jb 2026-10-14: "We are not moving to a larger instance for this").
- Memory on Fly (Logfire, 2026-10-14): 207 MiB usable. Before godt.no the process used 137–144 MiB with 16–23 MiB left. With godt.no a ranking is 1.3 MiB (0.7 before) and a place's offers 1.1 MiB; warming every rule and place at start-up added about 60 MiB, so each machine thrashed (I/O stalls of 12–14 s, start-up up to 16 s, the front page 3–6 s) and was killed before warming was done. Now nothing is warmed, 8 rankings are kept (`Queries.KEPT`), the places' offers are dropped with them, and datasets/ is read one file at a time with one copy of each ingredient name (src/adapters/datasets.py). The site process on a Mac, which reads 20–25 MiB above Fly: 149 MiB after start-up, 165 after 100 searches over many rules and places; it was 216 and 251 with godt.no before the fix, and 165 and 185 before godt.no. On Fly after the fix (b758bdd, 2026-10-14): start-up 0.87 s, the process 124–132 MiB with 38–50 MiB available, I/O stalls under 1 s, a new rule or place 145–199 ms and a search already made 19 ms.
- The app adds gzip, security headers and cache headers itself (src/adapters/web/main.py `headers`): hashed static files are immutable, pages, the front page too, 5 minutes. No stale-while-revalidate: with it a browser showed the page from before a deploy (2026-10-13). HEAD is answered like GET.
- Machines stop when idle (`min_machines_running = 0`), so the first visit after a quiet spell waits for a machine to start. Warm, the front page answered in about 110 ms from Norway (2026-10-13).
- When `CANONICAL_HOST` is set (to matris.app), every other host name 301s to it, except /helse. Nothing else in the code names the host.
- Tracing, metrics and logs go to Logfire (src/adapters/web/telemetry.py), only when the `LOGFIRE_TOKEN` Fly secret is set (jb 2026-10-13: "go full tilt on all options … make sure we get every insight metric we can into logfire"). Every request but /helse is a span with its full URL (the search text too, as in statsbudsjett), every request and response header, Fly's edge region (`http.request.header.fly_region`), `process.served` (0 for the first request after start, most likely the visit that woke the machine), `process.uptime`, and on the first request `startup.boot_to_first_request`; under it, spans for the arguments, the route, the search (`search.rules`, `search.clauses`, `search.corrected`, `search.total`, `search.relax`), each Jinja template, and at debug level the response's start and body. Fragments say `fragment.kept`; a HEAD says `http.request.method_original`. `visit.*` as in statsbudsjett: the referring host, `Sec-Fetch-Site`, `utm_*`, the click id's name.
- The visitor's IP never reaches Logfire (uvicorn's access log still prints it to Fly's logs): `net.peer.ip` and `client.address` are blanked as the span starts, and `Fly-Client-IP`, `X-Forwarded-For`, `Forwarded`, `Referer` (its host is `visit.referrer`), cookies and authorization are redacted before they become attributes (tests/test_telemetry.py).
- Metrics: `matris.searches` (per route, found or not), `matris.search.rules`, `matris.search.clauses`, `matris.search.results`, `matris.fragments`, `matris.dataset.age` and `matris.offers.left` (days; below 0 the offers are old), the HTTP server metrics, and on Fly the full system metrics: the machine is a Firecracker VM, so CPU per state (steal is time the host gave to others), memory, swap, disk, network, the process's CPU, memory, threads, file descriptors and garbage collection are its own; plus Linux pressure stall time (`system.linux.pressure.stall_time`). Logs: the `start-up` span, `ready` (dataset counts, offers, `startup.boot_to_ready`, `startup.process_to_ready`), `stopping after … s and … requests`, uvicorn's logs, Python warnings, event-loop callbacks over 100 ms, and Logfire's configuration log with the package versions. Every span carries Fly's machine (`fly.machine.id`, `fly.region`, `fly.image.ref`, `fly.vm.memory_mb`, …) and the commit, which the deploy job passes as `GIT_SHA`, so spans link to the code on GitHub.
- Fly stops an idle machine with SIGINT and kills it 5 s later (`kill_timeout`); uvicorn raises the signal again once it has shut down, so the app sends what Logfire has queued in its lifespan shutdown rather than leaving it to atexit.
