## 1. What this is

matris.app: dinner ideas from matprat.no that fit one household's diet, with the week picked from dinners whose main protein is on sale in Stavanger (mattilbud.no). jb's project, built on 2026-10-13, hosted on Fly.io at https://matris.app. The code is at https://github.com/janbjorge/ukemeny (jb 2026-10-13: `janbjorge/matris` is an older project); the app, the CLI and the Fly app are called matris.

- The menu is matris (the front page) and "Slik virker det" (jb 2026-10-13: "the 'ukens middag' and 'finn en middag' button / links are broken, merge or split the pages": both pointed at `/`, so they are gone; one page keeps the week following the diet picked in the search).
- `/` is "Ukens middager": the week (five dinners, one per main protein, fish up to twice but never the same fish), then "Finn en middag": a search box in plain bokmål (`/?q=rask+kylling+uten+sopp`, src/core/search.py, METHOD.md §6) and three rows of chips: "Kosthold" (13 diet rules: Vegetar, Vegansk, Pescetarianer, Glutenfri, Melkefri, Lite laktose, Uten løk, Uten hvitløk, Lav FODMAP, Lavkarbo, Uten svin, Uten alkohol, Gravid), "Allergier" (the 12 other EU allergens and Uten belgfrukter; jb 2026-10-13: "We need a shiton of kosthold filters, these three does not cut it"), both off until picked, "Hva slags" (prep time, on sale, godt likt, barnevennlig, with counts) and "Hovedråvare" (with counts; no Vegetar there, since it is a rule), and "Sorter": Anbefalt, Rabatt % and Rabatt kr (jb 2026-10-13: "We lack two sorting options, by releive (percent) and absolute, acctual discount"; the search words «rabatt i prosent» and «rabatt i kroner»). Then the count, typo notes, the dinners, and, when nothing matches, which part to drop. The site reads no profile.yaml (jb 2026-10-13): the rules come from the search, and the week follows them. Typing searches after 300 ms. Everything loads `/middager` as an HTMX fragment; without the `HX-Request` header it 303s to `/?q=…#forslag`, and with it the answer carries `HX-Replace-Url`, so the address bar is always a shareable link. A fragment also sends the week out of band, and, unless the request came from the box itself (`HX-Trigger` `q` or `sok`), the search box with its new text. The old `protein=` and `tilbud=` parameters still work; they become words in the search.
- Phones (jb 2026-10-13: "it needs tobe render super nice on smartphone"): under 640 px the week is a row of cards to swipe, each chip row is one line to swipe (chosen chips first), the search box stays pinned at the top of "Finn en middag", the Søk button is hidden (the keyboard's Søk sends; Enter also closes the keyboard), touch targets are at least 40 px, and hover effects only apply with a mouse. The ideas come 12 at a time; the list goes on as you scroll (jb 2026-10-13: "we still lack the inf scroll"): the "Vis flere" button after the cards loads the next 12 from `/middager/flere?q=…&fra=12` when it scrolls into view (`hx-trigger="intersect once, click"`), and without JavaScript it is a link to the front page with `antall`. Cards have no `content-visibility`: with it Firefox turned off scroll anchoring ("too many consecutive adjustments", jb 2026-10-13). Checked in WebKit at 320, 360, 390 and 1280 px wide: nothing wider than the screen. The stylesheet is inline in each page (8.1 kB gzipped for the front page, 2026-10-13), htmx loads deferred, and there is a web manifest and PNG icons (static/icon-192.png, icon-512.png, apple-touch-icon.png, drawn from icon.svg) for "Legg til på Hjem-skjerm". Speed (jb 2026-10-13: "serch is still an order of magnitude slower then i would like, nettwork duration shows 180 ms"): what does not depend on the diet rules is worked out once per process (core.ranking.prepare: protein, score, offers, and per dinner what it holds, whether it suits pregnant women or low FODMAP, and its carbohydrate; the search Index over every dish), so a new set of rules only judges the dinners no shortcut leaves out and adds a View. Each rule on its own is worked out in a thread after start-up (Queries.warm, 0.5 s locally). A fragment only carries the week when the rules change (HX-Current-URL). Rendered fragments are kept (512, newest last), so a search someone already made is not rendered again (2.7 ms locally, against 1.8 ms for /helse). Typing searches after 100 ms without a key (it was 300 ms); a newer search cancels one on its way. Chips and other search links start on mouse-down, the 80–120 ms before a mouse click lands; touch and keys start on the click, so swiping a chip row does not search. Infinite scroll starts loading from a mark 1 200 px above the end of the list. Locally a search took 3–5 ms after that, a new combination of rules up to about 25 ms, and a word searched for the first time 10–17 ms (it is then known for every set of rules); live, a warm search over a reused connection answered in 27 ms before these changes, and a new set of rules in up to 377 ms.
- Cards are calm (jb 2026-10-13: "this needs to die, also the hero cards er pretty busy"; "This clutter hell"): name, protein, prep time, rating (from 5 ratings), the main discount with its store (prices in the tooltip), and, when a picked rule needs one, the swaps in a few words («Bytt: glutenfri pasta · vårløk for løk», `Note.swap`). The label and kid notes («sjekk etiketten», choking) name ingredient after ingredient, so they are neither on the site nor in the API (jb 2026-10-13: "We still seem to leak matprat content"); only the CLI's text output, on this machine, shows them.
- Colours (src/adapters/web/static/app.css): light always, no dark theme (jb 2026-10-13: "its pretty dark"). Re-done the same day after "really poor contranst between some of the hero cards and there contents": an audit of 48 pairs found card edges invisible against the page (APCA Lc 0) and grey text and links on cream just under reading level. Every colour is now picked in OKLCH at one lightness per role (label text L 0.40 on tints L 0.955, solid protein colours L 0.50 with white text, text and surfaces on a warm neutral hue), protein hues are spread apart (fish blue 245, chicken amber 85, pork plum 332, …), and tests/test_palette.py checks 62 pairs with APCA (text and labels Lc ≥ 75, card edges ≥ 15) and WCAG 2 (≥ 4.5:1).
- `/om` ("Slik virker det") explains how recipes and offers connect (main protein, offers matched by word and a language model, a dinner on sale when its main protein is, the ranking and the week), how the search reads words (jb 2026-10-13: "We can sill explain abit more on how search works, and how it correlates the two datasources"), that a language model judged the ingredients, and a prompt to paste into an agent that points it at `/llms.txt` (jb 2026-10-13, after PgQueuer's "Let an agent introduce you").
- Agents follow links, never write them (jb 2026-10-13: ChatGPT read llms.txt, then said it could not fetch the week; the log shows it never asked the API, likely because ChatGPT opens only addresses it has seen). llms.txt starts with a link to the week for each diet rule, and every /api/plan and /api/middager answer has `links`: `add` and `remove` per diet rule, `plan` and `dinners` for the same search. `matris --json` has no `links`.
- For agents: `/llms.txt`, a read-only JSON API under `/api` (`/api/plan`, `/api/middager?q=`, `/api/oppskrift?url=`) with its schema at `/api/openapi.json` (absolute server URL, built from the request), CORS open. `/api` and `/api/` redirect to the schema (jb 2026-10-13). `/api/middager` returns `search` (`query` as understood, `understood` clauses, `corrected` words, `total`, and `without`: what to drop when nothing matches) and per dinner `matched`, the ingredients that hold a searched word. Every HTML page links both in `<head>` and a `Link:` header. `/robots.txt` lets ChatGPT-User, Claude-User and Perplexity-User (agents fetching for a person) open everything, and for other crawlers allows `/api/` and keeps them off `/?` and `/middager` (not `/*?`: Python's parser let that outrank `Allow: /api/`, closing the API's searches; jb 2026-10-13); `/sitemap.xml` lists `/` and `/om`.
- The `matris` CLI (src/adapters/cli.py) reads the same snapshot: `plan`, `candidates [SEARCH…]` (the same search, quotes optional), `check URL`, each with `--json` (one document on stdout, errors as `{"error": {"kind", "message"}}`, exit 1); `build` runs the offline build; `profile` edits profile.yaml.
- Stack (as statsbudsjett): Python 3.14, FastAPI + uvicorn + Jinja + HTMX, no other JavaScript. pydantic v2 in the adapters, orjson for JSON.

## 2. Layout

- `src/core/`: the pure domain. models.py (types; `Dish` and `Part` are what the site keeps, `Snapshot` holds them), dishes.py (full recipe → `Dish`), diet.py (`judge`: does a dish fit a `Household`), matching.py (offer word filter, weights, `main_protein`), ranking.py (`dinners`, `plan`, `pick`, `varied`), search.py (`parse` bokmål into clauses, `tags` per dinner, `Index` to find), ports.py, errors.py. Standard library only; tests/test_boundary.py enforces it.
- `src/app/queries.py`: read-only queries over the snapshot for the site, the API and the CLI (`plan`, `search`, `check`). The ranking and the search index are worked out once at start-up (the index in 0.03 s; a search with a new word took at most 9 ms, 2026-10-13).
- `src/app/build.py`: the offline use cases: `refresh` (recipes), `classify` (ingredients), `match` (offers), `snapshot`.
- `src/adapters/`: datasets.py (reads and writes `datasets/`, implements `core.ports.Datasets`), profile.py (profile.yaml with pydantic; also the list of grocery chains), schema.py (the JSON shape for API and CLI), cli.py, and `web/` (main.py, api.py, params.py for query strings, fmt.py for Norwegian numbers, templates, static).
- `src/pipeline/`: offline only, not in the Docker image. matprat.py, tjek.py, jev.py, datasets.py (the composition root: `uv run python -m pipeline.datasets`).
- `profile.yaml`: our household, for the CLI and the build's shopping area (§5); the site does not read it. `src/adapters/profile.example.yaml` is the template, identical today (tests/test_profile.py).

## 3. Sources

| What | Where | Read by |
|---|---|---|
| Recipes | https://www.matprat.no/sitemap.xml (4 479 recipe pages with `lastmod`), each page's `__NEXT_DATA__` | src/pipeline/matprat.py |
| Offers | Tjek's public API `https://squid-api.tjek.com/v2` (`/catalogs`, `/offers?catalog_ids=`), the service behind mattilbud.no. No key. | src/pipeline/tjek.py |

Site quirks:
- matprat's `__NEXT_DATA__` holds each ingredient's name, amount, unit and grocery department (`/kjøtt/kylling/høns`, `/melk/melkeprodukter`, `/glutenfritt`, `/melkefritt`), and `gtmDimensions.dimension8` = `Middagsrett` marks dinners (1 943 of 4 479). matprat's own main ingredient (`dimension1`) misfiles some dishes ("Kyllingfilet med spekeskinke" is Svin), so it is not used (METHOD.md §3).
- matprat's robots.txt disallows `/Services/` (its search API) and allows `/oppskrifter/`, so pages are read one by one. robots.txt asks for no crawl delay; 16 at a time read 300 pages in 29.5 s with no errors (2026-10-13), so a full crawl is about 7 minutes. It used to be 3 at a time with half a second between (about 40 minutes).
- Tjek: one location search stops at 1 000 offers, so offers are read per catalog. A catalog's listed `offer_count` can differ from what `/offers` serves (KIWI listed 109, served 105).
- Tjek also lists furniture, hardware and electronics catalogs; "Spar Kjøp" is building supplies. Only the chains in `GROCERS` (src/adapters/profile.py) are read.
- Before-prices: Tjek's `pre_price` field, or "Førpris 34,90" / "Før 48,9" in the catalog text (mostly Joker). On 2026-10-13, discounted/all offers per chain: Bunnpris 0/161, Matkroken 0/10, Europris 36/152, Coop Mega 47/119, KIWI 27/105, Extra 28/103, REMA 1000 27/89, Joker 39/68, Obs 9/50, Coop Prix 10/45, MENY 11/35, Coop Marked 4/32, SPAR 14/28.
- Coop Mega prices some weighed goods per 100 g against a before-price per kg ("29,90 … Pr kg 299,00. Førpris 339,00 pr kg"), which read as 91 % off instead of 12 % (METHOD.md §4).

## 4. Data and the weekly build

- `datasets/` is committed and is all the site reads: dishes.json (1 943 dinners, 3.6 MB), traits.json (1 148 ingredient names, 0.2 MB), offers.json (`built`, 997 offers, and `matches`: per ingredient name the offer ids that are that ingredient; 159 names this week, 0.3 MB).
- A dish in dishes.json is facts, no rules (jb 2026-10-13: "there are loads of other constaints that might apply, so we can not have these attched to the dish"): name, URL, portions, prep time, rating, and per ingredient its name, matprat department, unit and grams per portion rounded to 5 g. No ingredient wording and no method: the repo is public and the recipes stay on matprat.no (docs/plan-web.md). Every rule (lactose, onion, main protein, discount weight) is worked out from these and the traits at runtime.
- `uv run python -m pipeline.datasets` (or `matris build`) builds it from scratch, with no options and nothing kept between runs (jb 2026-10-13: "one thing, and one thing only, refresh from the sources, and build up or dataset, from scratch every time"; "ive told you to clean up the fucing cli"): every recipe page on matprat.no (4 479 pages, 16 at a time, about 7 minutes), this week's catalogs, every Jev label of every ingredient and every offer match. It needs `TYPESAFE_API_KEY`, prints a line as each step starts (matprat.no, Jev's labels, mattilbud.no, Jev's matches) and its count about every tenth (jb 2026-10-13: "THe cli needs some light output so i know whats going on"). `-v` adds speed, time left, time and Jev cost per step, failed pages, retries and the catalogs; `-vv` a line per page, ingredient (its labels), offer match and Jev call; `-vvv` every HTTP request (jb 2026-10-13: "i want a -v -vv or -vvv that gives more insight into whats going on"). `matris build -v` is the same. Commit and push afterwards to deploy. When jb asks for new data, the agent runs it.
- The site marks the offers as stale when the median offer end date has passed (src/app/queries.py `stale`).

## 5. The household and profile.yaml

- `diet`: onion, gluten, garlic each `avoid`, `note` or `ok`; `onion_substitute` (vårløk: fine for us and stands in for onion); `lactose` (grams per adult portion still fine, 3); `swaps` (false: only dinners needing no swap). `small_kids` (notes for chili and choking risks; no ages, since the repo is public). `shopping` (`lat`, `lng`, `radius_km`, `stores`). `week` (`dinners` 5, `fish` 2, `on_sale_only`).
- The site does not read profile.yaml. The CLI's base household is the profile's `diet` and `small_kids`; the words «uten løk», «glutenfri» and «lite laktose» in a CLI search add to it. `shopping` tells the offline build where to read offers. The Docker image does not contain the file.

## 6. Jev

- TypeSafe's Jev (typesafe_sdk, `jev-latest`, jev-1.13.0 on 2026-10-13), as in ezwork. Only the offline build calls it, at most 8 requests at a time.
- Ingredients: one Choice per label, from a registry (src/pipeline/jev.py `ingredient_labels`, keys in core.models.LABELS; jb 2026-10-13: "i want some kind of Choice regresety"): gluten yes/maybe/no, onion/garlic/maybe/none, lactose none/trace/some/high, kids ok/spicy/choking, then yes/maybe/no for each core.models.Item (the 13 EU allergens besides gluten, legumes, meat, animal origin, pork, alcohol), FODMAP low/moderate/high, carbohydrate per 100 g none/low/medium/high, and Mattilsynet's advice for pregnant women ok/limit/avoid. The state is the ingredient name and its matprat department. Every label of every ingredient is asked on every build, all in one request per ingredient.
- Offers: one yes/no question per offer heading, with the offer's text in the question, all in one request per ingredient. Every (ingredient, heading) pair is asked on every build, except that an exact name match or a snack/pålegg heading is answered without asking (src/core/matching.py `obvious`).
- What the probes showed (METHOD.md §2 has the judgement calls): Norwegian examples in the criteria fixed purre, risnudler, tamari and matfløte; the department fixed 28 of 36 wrong answers on rarer words; a single Choice over offers dropped right answers, and questions pointing at `offers[i]` mixed offers up. The new labels, probed on 64 hard ingredients (2026-10-13, /tmp/probe): 126 of 127 expected answers right at first, with vineddik and eggnudler as milk and dijonsennep as egg among the rest; naming them in the criteria made it 127 of 127 and cleared those three. That probe was 64 calls, 221 k tokens, $0.009.
- Cost: the first full classification and matching of 1 943 dinners was 1 503 calls, about 1.8 M input tokens, $0.074. Each build now asks everything again (about 1 150 ingredient calls plus the offer matching).
- Known wrong answers still in traits.json: hurtigris, malt allehånde and frossen lapskausblanding as gluten; gulbete and strutsevingknopper as onion.
- The full run of the new labels (2026-10-13, 36 s for 1 148 ingredients) had vann as animal origin (526 uses), every mushroom as maybe meat, animal and milk, sylteagurk as fish, ørretrogn and laksekotelett as egg, and akevitt as milk; a check of each label against matprat's department found them. Naming them in the criteria fixed them, and asking milk, egg, fish, meat and animal again (1 148 calls, $0.060) put the fix in traits.json. Still wrong in that probe: portobellosopp and laksekotelett as maybe milk, tortillalefse as milk.

## 7. Hosting

- Dockerfile: python:3.14-slim plus uv, runtime dependencies only, no `src/pipeline/`, runs as `nobody`. The image is 406 MB and the app used 67 MiB of memory locally (2026-10-13). fly.toml: app `matris`, region arn, health check /helse, machines stop when idle, shared-cpu-1x with 256 MB.
- The app adds gzip, security headers and cache headers itself (src/adapters/web/main.py `headers`): hashed static files are immutable, pages 5 minutes. No stale-while-revalidate: with it a browser showed the page from before a deploy (2026-10-13). HEAD is answered like GET.
- Machines stop when idle (`min_machines_running = 0`), so the first visit after a quiet spell waits for a machine to start. Warm, the front page answered in about 110 ms from Norway (2026-10-13).
- When `CANONICAL_HOST` is set (to matris.app), every other host name 301s to it, except /helse. Nothing else in the code names the host.
- Tracing, metrics and logs go to Logfire (src/adapters/web/telemetry.py), only when the `LOGFIRE_TOKEN` Fly secret is set (jb 2026-10-13: "go full tilt on all options … make sure we get every insight metric we can into logfire"). Every request but /helse is a span with its full URL (the search text too, as in statsbudsjett), every request and response header, Fly's edge region (`http.request.header.fly_region`), `process.served` (0 for the first request after start, most likely the visit that woke the machine), `process.uptime`, and on the first request `startup.boot_to_first_request`; under it, spans for the arguments, the route, the search (`search.rules`, `search.clauses`, `search.corrected`, `search.total`, `search.relax`), each Jinja template, and at debug level the response's start and body. Fragments say `fragment.kept`; a HEAD says `http.request.method_original`. `visit.*` as in statsbudsjett: the referring host, `Sec-Fetch-Site`, `utm_*`, the click id's name.
- The visitor's IP is recorded nowhere: `net.peer.ip` and `client.address` are blanked as the span starts, and `Fly-Client-IP`, `X-Forwarded-For`, `Forwarded`, `Referer` (its host is `visit.referrer`), cookies and authorization are redacted before they become attributes (tests/test_telemetry.py).
- Metrics: `matris.searches` (per route, found or not), `matris.search.rules`, `matris.search.clauses`, `matris.search.results`, `matris.fragments`, `matris.dataset.age` and `matris.offers.left` (days; below 0 the offers are old), the HTTP server metrics, and on Fly the full system metrics: the machine is a Firecracker VM, so CPU per state (steal is time the host gave to others), memory, swap, disk, network, the process's CPU, memory, threads, file descriptors and garbage collection are its own; plus Linux pressure stall time (`system.linux.pressure.stall_time`). Logs: the `start-up` and `warm the diet rules` spans, `ready` (dataset counts, offers, `startup.boot_to_ready`, `startup.process_to_ready`), `stopping after … s and … requests`, uvicorn's logs, Python warnings, event-loop callbacks over 100 ms, and Logfire's configuration log with the package versions. Every span carries Fly's machine (`fly.machine.id`, `fly.region`, `fly.image.ref`, `fly.vm.memory_mb`, …) and the commit, which the deploy job passes as `GIT_SHA`, so spans link to the code on GitHub.
- Fly stops an idle machine with SIGINT and kills it 5 s later (`kill_timeout`); uvicorn raises the signal again once it has shut down, so the app sends what Logfire has queued in its lifespan shutdown rather than leaving it to atexit. Checked in the Docker image with Fly's environment set (2026-10-13): everything above arrived and the visitor's IP was nowhere. Telemetry adds to each start: imports 21–25 ms, configuring 49–53 ms.
- Fly's own metrics (edge latency, proxy concurrency, CPU throttling and burst balance, OOM kills) are only in Fly's Prometheus (`https://api.fly.io/prometheus/<org>/federate`). Getting them into Logfire needs an OpenTelemetry Collector app that is always on (about $2.27/month in arn); jb chose to keep to what the app sees (2026-10-13).
- Pushes to main run ruff, ty and pytest and then `flyctl deploy` (.github/workflows/deploy.yml). The FLY_API_TOKEN secret is a deploy token for `matris` named github-actions-ukemeny (2026-10-13); the first run via Actions released v2. Fly's own GitHub integration is not used, since it would deploy a second time and skip the checks.
